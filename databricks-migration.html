Contexto

El reporte había crecido hasta depender de transformaciones de Power Query sobre datasets de millones de filas y más de una docena de dimensiones de negocio. El problema ya no era una fórmula lenta: era la ubicación de la lógica.

Cada actualización obligaba a Power BI o Excel a descargar, combinar y transformar demasiado volumen. Esto hacía el flujo frágil, difícil de mantener y poco escalable.

Por qué el enfoque anterior no escalaba

  • Transformaciones repetidas en el cliente en lugar de una capa compartida.
  • Joins y agregaciones sobre millones de filas durante cada refresh.
  • Jerarquías financieras parent-child difíciles de consumir directamente.
  • Poca separación entre preparación de datos, modelo semántico y visualización.

Rediseño por capas

La migración llevó la lógica pesada a Databricks y dejó Power Query para conexiones y ajustes livianos. Esto convirtió el flujo en una arquitectura con responsabilidades más claras.

Power BI model
SQL · illustrative aggregation view
CREATE OR REPLACE VIEW reporting.v_account_month AS
SELECT
  fiscal_month,
  region,
  account_id,
  SUM(gross_sales) AS gross_sales,
  SUM(net_sales) AS net_sales,
  SUM(account_contribution) AS account_contribution
FROM curated.financial_fact
GROUP BY fiscal_month, region, account_id;

Transformación de jerarquías financieras

Las estructuras parent-child no eran ideales para filtros y matrices en Power BI. Se desarrolló lógica para recorrer la relación padre-hijo y producir columnas de nivel consistentes.

El resultado fue una tabla plana L1-L20 que podía unirse a los hechos financieros y ofrecer drill-down estable en el modelo semántico.

PySpark · illustrative hierarchy step
# Build a level-based hierarchy table for reporting
levels = ["L1", "L2", "L3", "L4"]
result = base
for level in levels:
    result = result.join(
        parent_lookup.alias(level),
        result["parent_id"] == col(f"{level}.member_id"),
        "left"
    )

Controles de calidad

Mover lógica a Databricks no era suficiente; había que demostrar que la nueva salida era equivalente y más confiable.

  • Comparación de row counts por periodo y región.
  • Reconciliación de sumas antes y después de la migración.
  • Pruebas de claves huérfanas y miembros sin jerarquía.
  • Validación de granularidad para evitar duplicación en joins.
